## ADD-07 — Статистика за датами Sessions (параметр `basis`)

| Параметр | Значення |
|---|---|
| Нова вимога | REQ-F-022b |
| Пов'язані вимоги | REQ-F-022, REQ-F-022a, REQ-F-012, REQ-F-013 |
| Ендпоїнт | `GET /stats?period=&basis=` |
| Тип | адендум |

---

### SRS (до SG: лише опис, не вносити в srs.md)

**REQ-F-022** (діюча): «Система відображає особисту статистику: кількість
елементів зі статусом "completed", розбиту за типом і часовим діапазоном.»

**REQ-F-022b** (нова, вноситься після SG):

> Система надає альтернативний режим статистики на основі дат Sessions
> (`basis=sessions`). У цьому режимі підраховуються Sessions (акти перегляду /
> читання), а не елементи зі статусом "completed". Кожна Session враховується у
> тому місяці/році, до якого належить її поле `date`. Елемент може потрапити до
> кількох часових діапазонів, якщо у нього кілька Sessions у різні місяці.

---

### API

**Новий необов'язковий параметр** `basis` для `GET /stats`:

```
GET /stats?period={month|year|all}&basis={completedAt|sessions}
```

| `basis` | Значення |
|---|---|
| `completedAt` | **(дефолт)** поведінка ADD-05 — рахує елементи з `status=completed`, фільтрує за `Item.completedAt` |
| `sessions` | рахує Sessions, фільтрує за `Session.date` |

**Схема відповіді** — однакова для обох basis:

```json
{
  "period":  "month",
  "basis":   "sessions",
  "books":   3,
  "series":  1,
  "films":   2,
  "total":   6
}
```

Поле `basis` додається до відповіді (раніше відсутнє) з дефолтом `"completedAt"`.

---

### Семантичні рішення (обов'язкові для реалізації)

#### Рішення 1 — Completed без Sessions при basis=sessions

**Питання:** Якщо елемент має `status=completed`, але жодної Session, чи рахується він
при `basis=sessions`?

**Рішення: НЕ рахується.**

`basis=sessions` рахує саме акти перегляду/читання (Session-записи). Відсутність
Session означає відсутність факту перегляду в журналі. Елемент з`status=completed`
і без Sessions не впливає на цю статистику.

**Наслідок для користувача:** якщо користувач не веде Sessions, `basis=sessions`
завжди повертає нулі. README повинен пояснювати, що `basis=sessions` вимагає
наявності Session-записів.

---

#### Рішення 2 — Stats.total при basis=sessions

**Питання:** `Stats.total` = кількість Sessions чи унікальних елементів?
Як рахується елемент із двома Sessions в одному місяці?

**Рішення: Stats.total = сума Sessions (не унікальних елементів).**

| Ситуація | Результат |
|---|---|
| 1 фільм, 1 Session в листопаді | `films: 1, total: 1` |
| 1 фільм, 3 Sessions в листопаді | `films: 3, total: 3` |
| 1 фільм, 2 Sessions (листопад + жовтень) | листопад: `films: 1`; жовтень: `films: 1` |
| 2 книги, 1 Session кожна в листопаді | `books: 2, total: 2` |

Семантика `basis=sessions` — «скільки переглядів/прочитань зафіксовано за
період», а не «скільки унікальних елементів».

**Наслідок:** клієнт може відображати підказку «X переглядів» замість «X фільмів»
при `basis=sessions`, хоча схема відповіді однакова.

---

#### Рішення 3 — Sessions елементів зі статусом ≠ completed

**Питання:** Чи враховуються Sessions елементів із `status=in_progress`, `planned`, `on_hold`?

**Рішення: Так, враховуються.**

`basis=sessions` рахує всі Sessions незалежно від поточного статусу елемента.
Обґрунтування:

1. Session фіксує факт перегляду, який може відбутися до завершення елемента.
2. Статус елемента може змінитись після запису Session (напр.: `in_progress` → `completed`).
3. Режим `basis=sessions` моделює активність перегляду, а не стан завершення.

**Відмінність від basis=completedAt**, де враховуються лише елементи з
`status=completed`.

---

#### Рішення 4 — Статус ADD-05

ADD-05 (docs/api-addendum.md, розділ «ADD-05 — Статистика фільтрується за
`Item.completedAt`») зберігається без змін. Він документує поведінку за
замовчуванням (`basis=completedAt`), яка не порушена.

До ADD-05 після SG додається примітка:

> _Оновлено ADD-07 (spec/addendum-07.md): поведінка basis=completedAt залишається
> незмінною. ADD-07 вводить basis=sessions як альтернативний режим._

### Acceptance Criteria (AC-040 … AC-049)

#### Позитивні сценарії

| AC | Вимога | Критерій прийняття |
|---|---|---|
| AC-040 | REQ-F-022b | При `basis=sessions` і `period=all` повертаються counts Sessions по типу (book/series/film) і total = їх сума |
| AC-041 | REQ-F-022b | При `basis=sessions` і `period=month` рахуються тільки Sessions з `date` у поточному місяці |
| AC-042 | REQ-F-022b | При `basis=sessions` і `period=year` рахуються тільки Sessions з `date` у поточному році |
| AC-043 | REQ-F-022b | Один елемент з двома Sessions в одному місяці дає count=2 для свого типу, не 1 |
| AC-044 | REQ-F-022b | Без параметра `basis` (або `basis=completedAt`) відповідь ідентична поведінці ADD-05: зворотна сумісність не порушена |

#### Негативні та граничні сценарії

| AC | Вимога | Критерій прийняття |
|---|---|---|
| AC-045 | REQ-F-022b | Елемент зі статусом `completed` без Sessions при `basis=sessions` → не рахується (count=0 для його типу) |
| AC-046 | REQ-F-022b | Session елемента з `status=in_progress` при `basis=sessions` → рахується |
| AC-047 | REQ-F-022b | `basis=invalid` → 400 VALIDATION_ERROR з `field: "basis"` |
| AC-048 | REQ-F-022b | Порожній каталог (або всі статуси ≠ completed, жодної Session) при будь-якому basis → `{books:0, series:0, films:0, total:0}` |
| AC-049 | REQ-F-022b | Session з датою в останній день місяця рахується в тому місяці (не наступному); Session з датою в перший день нового місяця — у новому місяці |

### Обґрунтування

**Чому basis=sessions не замінює basis=completedAt:**  
Два режими вирішують різні питання. `completedAt` відповідає: «Скільки нових
завершених елементів за місяць?» (прогрес за каталогом). `sessions` відповідає:
«Скільки переглядів відбулося за місяць?» (активність перегляду). Обидва
корисні, і жоден не є помилкою ADD-05.

**Чому дефолт — completedAt:**  
Зворотна сумісність. Всі існуючі клієнти і тести очікують поведінки ADD-05.
Явний параметр `basis=sessions` — opt-in у нову семантику.

**Чому total = sum Sessions (не unique items):**  
Якщо total = unique items, то повторний перегляд фільму в тому ж місяці не
відображається у статистиці — а це саме та проблема, яку вирішує ADD-07.
Семантика «кількість актів перегляду» більш послідовна для Sessions-режиму.
