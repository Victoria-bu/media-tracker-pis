# API Design Addendum v1.0

**Версія:** 1.0.0
**Дата:** 2026-10-29
**Джерело:** spec/openapi.yaml, docs/api-design.md
**Підстава:** лабораторна робота, крок 14 (Частина 4)

> Цей документ фіксує поведінку API, яку SRS не описує явно, але яка необхідна
> для коректного контракту між клієнтом і сервером. Кожен пункт є
> **уточненням** (деталізує наявну вимогу) або **адендумом** (додає нову
> поведінку без протиріччя з SRS).

---

## 1. Статус `on_hold` — snake_case у API

| Параметр | Значення |
|---|---|
| Вимога | REQ-F-006 |
| Тип | уточнення |

**SRS:** перелік статусів у вигляді рядків для UI: `"planned"`, `"in progress"`,
`"completed"`, `"on hold"`.

**API:** enum `ItemStatus` у OpenAPI використовує snake_case для всіх значень із
пробілом: `in_progress`, `on_hold`. Решта незмінні: `planned`, `completed`.

**Обґрунтування:** JSON-значення не можуть містити пробіл в обліку JSON Schema
enum; snake_case є стандартом для machine-readable ідентифікаторів.

## 2. HTTP 409 при повторній реєстрації з тим самим email

| Параметр | Значення |
|---|---|
| Вимога | REQ-F-001 |
| Ендпоїнт | `POST /auth/register` |
| Тип | уточнення |

**SRS (BDD):** «Повторна спроба реєстрації з тим самим email показує повідомлення
"An account with this email already exists"» — задано текст помилки, але не
HTTP-статус.

**API:** повертає `409 EMAIL_TAKEN` із полем `field: "email"`.

**Обґрунтування:** 409 Conflict — семантично правильний код для конфлікту
унікальності ресурсу; клієнт може відрізнити конфлікт (409) від помилки
валідації (400) без парсингу тіла відповіді.

---

## 3. HTTP 409 при повторному додаванні елемента до тієї самої добірки

| Параметр | Значення |
|---|---|
| Вимога | REQ-F-015 |
| Ендпоїнт | `POST /collections/{id}/items` |
| Тип | адендум |

**SRS:** REQ-F-015 описує many-to-many зв'язок і дозволяє елементу належати
кільком добіркам одночасно. Поведінка при спробі додати елемент, що вже є
в добірці, не визначена.

**API:** повертає `409 ITEM_ALREADY_IN_COLLECTION` (без поля `field`).

**Обґрунтування:** без явного конфлікту сервер міг би мовчки ігнорувати запит
(idempotent) або створити дублікат рядка. 409 зберігає семантику 201 (успішне
додавання) незмінною і дає клієнту чіткий сигнал без зайвої логіки перевірки.

## 4. Сортування Sessions на сервері (новіші — першими)

| Параметр | Значення |
|---|---|
| Вимога | REQ-F-013 |
| Ендпоїнт | `GET /items/{id}/sessions` |
| Тип | уточнення |

**SRS:** REQ-F-013 — «відображення Sessions у зворотньому порядку та їх
кількість» — порядок згадується, але де він визначається (сервер чи клієнт)
не вказано.

**API:** сервер повертає сесії відсортованими від найновішої до найстарішої
(поле `date` DESC). Клієнт не сортує.

**Обґрунтування:** сортування на сервері гарантує однаковий порядок для всіх
клієнтів і узгоджується з принципом «клієнт не виконує нічого, крім UI-логіки»
(api-design.md §1).

## 5. Статистика фільтрується за `Item.completedAt`, а не за датою Session

| Параметр | Значення |
|---|---|
| Вимога | REQ-F-022 |
| Ендпоїнт | `GET /stats?period=` |
| Тип | уточнення |

**SRS:** REQ-F-022 — «кількість елементів зі статусом "completed" за типом і
часовим діапазоном» — не уточнює, яке поле дати є підставою для фільтру.

**API:** `period` фільтрує за `Item.completedAt` (дата завершення елемента),
а не за датою будь-якої Session.

**Обґрунтування:** `completedAt` — атрибут самого елемента (REQ-F-021), що
відповідає на питання «коли завершено»; дата Session відповідає на питання
«коли переглянуто», і для статистики завершень релевантна саме перша.

## 6. Ресурси іншого користувача повертають 404, а не 403

| Параметр | Значення |
|---|---|
| Вимога | REQ-NF-002 |
| Тип | адендум |

**SRS:** REQ-NF-002 описує захист облікових записів; поведінка при спробі
звернутися до ресурсу іншого користувача не задана.

**API:** будь-який захищений ресурс, що належить іншому користувачу, повертає
`404 NOT_FOUND` (а не `403 Forbidden`).

**Обґрунтування:** 403 підтверджує факт існування ресурсу (лише доступ
заборонено); 404 не розкриває інформацію про чужі дані. Це стандартна практика
privacy-by-design для однокористувацьких систем.
