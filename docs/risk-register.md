# Реєстр ризиків — Media Tracker v1

## R-01  Корельована помилка тест + код (AI-специфічний, високий)

**Прояв:** агент пише Test і Feature в одній або суміжних сесіях,
тлумачить вимогу однаково в обох — тести зелені, але поведінка не
відповідає SRS (напр., Sessions відсортовані не в той бік, каскадне
видалення з добірок не спрацьовує).

**Наслідки:** прихований баг доходить до Validation або продакшну;
переробка Feature після Gate.

**Спосіб виявлення:** ручна Validation-перевірка за чеклістом AC ID;
Gate-ревізія людиною незалежно від агента.

**Пом'якшення:**
- Людина читає тест перед стартом реалізації Feature
- При Validation звіряти поведінку з текстом AC, не лише з
  результатом автотестів
- BDD-сценарії з SRS використовуються як "другий погляд" при
  Validation

---

## R-02  Неправильне тлумачення вимоги агентом (AI-специфічний, високий)

**Прояв:** агент реалізує вимогу, що семантично близька, але не
відповідає SRS — напр., REQ-F-013 "зворотний хронологічний порядок"
реалізовано як прямий.

**Наслідки:** невідповідність AC; виявляється лише при Validation
або RELEASE-GATE; потрібне виправлення.

**Спосіб виявлення:** кожен Issue явно посилається на REQ ID та AC
ID; Validation виконується людиною за AC-чеклістом.

**Пом'якшення:**
- Issue містить REQ ID та AC ID — агент звіряється з ними перед
  реалізацією
- Для нетривіальної логіки (Sessions, Collections, каскадне
  видалення — Issue 3) — окремий інтеграційний тест
- При Validation людина самостійно проходить сценарій вручну, не
  покладаючись лише на звіт агента

---

## R-03  Недетермінованість між сесіями агента (AI-специфічний, середній)

**Прояв:** рішення, прийняті в різних сесіях агента (різних Issue),
несумісні між собою — напр., різний формат дат у Issue 2 і Issue 3,
різна назва API-маршрутів.

**Наслідки:** інтеграційні проблеми при переході між Issue;
рефакторинг уже зробленого.

**Спосіб виявлення:** повний регресійний прогін тестів при
завершенні кожного Issue (перед переходом до наступного).

**Пом'якшення:**
- Після Issue 1 зафіксувати ключові архітектурні рішення в одному
  файлі (напр. `CONVENTIONS.md`): стек, формати дат, назви таблиць
- Перед стартом кожного наступного Issue агент читає цей файл
- Gate-рішення перед переходом включає перевірку сумісності з
  попередніми Issue

---

## R-04  Втрата контексту в довгих сесіях (AI-специфічний, середній)

**Прояв:** агент "забуває" рішення з ранніх Issue — напр., структуру
зв'язку many-to-many, прийняту в Issue 2 чи 3 — і вигадує її заново
в Issue 4.

**Наслідки:** несумісний код, зламані тести попередніх Issue.

**Спосіб виявлення:** повний тест-ранер при завершенні кожного Issue.

**Пом'якшення:**
- `CONVENTIONS.md` як "журнал рішень", оновлюється людиною після
  кожного Gate-переходу
- Кожен новий запит до агента містить посилання на цей файл
- Великі Issue розбиваються на короткі ітерації всередині (кілька
  окремих запитів до агента, а не один величезний)

---

## R-05  Помилки агента з git/файлами (AI-специфічний, середній)

**Прояв:** агент виконує небезпечну git-команду (`git reset --hard`),
перезаписує незакомічені зміни, або комітить зайве (`.env`,
бінарні файли).

**Наслідки:** втрата роботи; пошкоджена git-історія.

**Спосіб виявлення:** `git status` і `git log` після кожної взаємодії
з агентом.

**Пом'якшення:**
- Робота над кожним Issue — в окремій гілці; злиття в main лише
  після ручної перевірки
- Явна заборона деструктивних git-операцій без підтвердження
  людини (прописати в промпті/CONVENTIONS.md)
- Перед і після кожної сесії з агентом — перевірка `git status`

---

## R-06  Недостатній людський контроль на Gate (AI-специфічний, середній)

**Прояв:** Gate підписується формально ("тести зелені — ок"), без
реальної перевірки відповідності AC.

**Наслідки:** приховані помилки накопичуються між Issue; виявляються
лише на RELEASE-GATE, коли виправлення вже дорожче.

**Спосіб виявлення:** фінальний наскрізний acceptance-сценарій на
RELEASE-GATE — але це пізній і дорогий момент для виявлення.

**Пом'якшення:**
- Validation кожного Issue має конкретний чекліст AC ID, а не
  загальну оцінку "виглядає нормально"
- Орієнтовний ліміт часу на Validation одного Issue (див. таблицю
  в plan.md) — не пропускати цей крок "для економії часу"

---

## R-07  Scope creep — агент додає функціонал поза SRS (середній)

**Прояв:** агент "покращує" код — додає пагінацію, email-підтвердження,
сортування тегів тощо, яких немає в жодному REQ-F.

**Наслідки:** непокрита кодова база; порушення простежуваності
REQ→AC→Test→Code.

**Спосіб виявлення:** під час Validation людина звіряє реалізоване
з конкретним REQ ID Issue; усе зайве — видаляється або виноситься
окремим адендумом, якщо справді корисне.

**Пом'якшення:**
- Кожен Issue явно вказує перелік REQ ID, що реалізуються — нічого
  поза цим списком
- Перед стартом Issue агент отримує посилання на Appendix A SRS
  ("Features Outside the MVP Scope"), щоб не реалізовувати це

---

## R-08  Складність Sessions і many-to-many Collections (технологічний, середній)

**Прояв:** некоректна робота каскадного видалення при одночасній
належності елемента кільком добіркам; проблеми з датами Sessions
(часові пояси).

**Наслідки:** порушення NF-003 (цілісність даних) або некоректна
поведінка, що відповідає за REQ-F-009/F-015/F-019 у Issue 3.

**Спосіб виявлення:** окремий інтеграційний тест на каскадне
видалення (Issue 3); ручна Validation BDD-сценарію "Item in Multiple
Collections" і "Deleting an Item with Cascade Removal".

**Пом'якшення:**
- Архітектурне рішення (як саме реалізовано зв'язок many-to-many
  і каскад — на рівні БД чи на рівні застосунку) фіксується до
  старту Issue 3 і записується в CONVENTIONS.md
- Тест покриває граничні випадки: елемент у 0, 1 і кількох добірках

---

## R-09  Автодоповнення тегів складніше за очікування (технологічний, низький)

**Прояв:** реалізація автодоповнення (REQ-F-010) виявляється
повільнішою чи складнішою, ніж очікувалось.

**Наслідки:** затримка Issue 3; розмитий критерій AC-010.

**Спосіб виявлення:** Test-тікет Issue 3 покриває автодоповнення;
Validation — ручна перевірка.

**Пом'якшення:**
- Спрощений підхід за замовчуванням: клієнтський prefix-match по
  вже завантаженому списку тегів користувача (без окремого API
  для пошуку)
- Якщо реалізація виходить за розумний час — повернутись до цього
  спрощеного варіанту, не ускладнювати далі

---

## R-10  Затримки людської перевірки стопорять конвеєр (ресурси/строки, низький)

**Прояв:** через навчання/інші справи немає часу вчасно перевірити
Issue — агент (і прогрес) простоює між Issue.

**Наслідки:** загальне затягування завершення проєкту.

**Спосіб виявлення:** відкритий Issue довше запланованого часу з
таблиці Validation (`docs/plan.md`).

**Пом'якшення:**
- Орієнтовний ліміт на Validation кожного Issue (із `docs/plan.md`)
  — відстежувати, чи не перевищується він систематично
- Поки Issue очікує перевірки — можна паралельно готувати наступний
  промпт або документацію, не зупиняючи весь процес повністю
