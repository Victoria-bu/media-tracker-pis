**Версія:** 1.0.0  
**Джерело вимог:** spec/srs.md

## 1. Розподіл функціональних вимог: API / клієнт

**Принцип розподілу:** все, що змінює або зберігає стан (БД, сесія, файли) — API. Фільтрація, сортування, пошук і UI-реакції (форма, автозаповнення дати) — клієнт, оскільки каталог містить до 100 елементів (AC-034) і завантажується повністю одним запитом.

**Підсумок:** API — 18, Клієнт — 9, API + клієнт — 3.

| ID | Вимога (коротко) | Де реалізується | Обґрунтування |
|---|---|---|---|
| REQ-F-001 | Реєстрація (email, пароль, нікнейм) | API | Дані зберігаються в БД; сервер перевіряє унікальність email |
| REQ-F-002 | Вхід за email і паролем | API | Сервер перевіряє credentials та видає HTTP-only cookie (REQ-NF-007) |
| REQ-F-003 | Вихід із системи | API | Сервер анулює сесійний cookie; без серверного виклику cookie залишиться валідним |
| REQ-F-004 | Відображення каталогу | API | Список елементів зберігається в БД — GET /items повертає дані |
| REQ-F-005 | Фільтр каталогу за типом | Клієнт | Усі елементи вже завантажені; фільтрація в браузері без нового запиту |
| REQ-F-006 | Фільтр каталогу за статусом | Клієнт | Локальна фільтрація вже завантажених даних |
| REQ-F-007 | Додавання нового елемента | API | Запис нової сутності в БД — POST /items |
| REQ-F-008 | Редагування атрибутів елемента | API | Оновлення запису в БД — PATCH /items/:id |
| REQ-F-009 | Видалення елемента (каскадно з колекцій) | API | Сервер видаляє елемент і всі зв'язки з колекціями в одній транзакції |
| REQ-F-010 | Теги + автодоповнення | API + клієнт | Теги зберігаються в БД разом з елементом; список наявних тегів завантажується для підказок; UI-фільтрація підказок — клієнт |
| REQ-F-011 | Фільтр каталогу за тегом | Клієнт | Теги вже включені у відповідь GET /items; локальна фільтрація в браузері |
| REQ-F-012 | Додавання Session (дата, рейтинг, нотатка) | API | Session — окрема сутність у БД — POST /items/:id/sessions |
| REQ-F-013 | Відображення Sessions (зворотній порядок, кількість) | API | Список і лічильник повертає GET /items/:id/sessions, порядок newest→oldest задає сервер |
| REQ-F-014 | Редагування / видалення Session | API | Зміна або видалення запису в БД — PATCH/DELETE /items/:id/sessions/:sid |
| REQ-F-015 | Додавання елемента до кількох колекцій | API | Many-to-many зв'язок зберігається в БД |
| REQ-F-016 | Створення колекції | API | Нова сутність Collection в БД — POST /collections |
| REQ-F-017 | Перейменування колекції | API | Оновлення запису в БД — PATCH /collections/:id |
| REQ-F-018 | Видалення колекції (без видалення елементів) | API | Сервер видаляє лише колекцію та її зв'язки, не торкаючись елементів каталогу |
| REQ-F-019 | Вилучення елемента з колекції | API | Видалення рядка many-to-many у БД |
| REQ-F-020 | Відображення вмісту колекції | API | GET /collections/:id повертає список елементів із назвою, типом, статусом |
| REQ-F-021 | Автозаповнення дати завершення | Клієнт | При зміні статусу на «завершено» форма підставляє поточну дату в порожнє поле; фактичне збереження відбувається через REQ-F-008 |
| REQ-F-022 | Особиста статистика за типом і періодом | API | Агрегація в БД із фільтрами по статусу, типу та даті — GET /stats?period=… |
| REQ-F-022a | UI-селектор часового діапазону для статистики | Клієнт | Компонент вибору передає обраний параметр як query-параметр до API-запиту REQ-F-022 |
| REQ-F-023 | Пошук у каталозі за назвою | Клієнт | Локальна фільтрація вже завантаженого масиву без додаткового запиту |
| REQ-F-024 | Поля, специфічні для типу, у формі | Клієнт | Показ/приховання полів залежно від вибраного типу — виключно логіка UI |
| REQ-F-025 | Обкладинка: дефолтна або своя | API + клієнт | Дефолтна ілюстрація — клієнт (статичний asset за типом); завантаження свого зображення — API (multipart upload) |
| REQ-F-026 | Сортування каталогу | Клієнт | Локальне сортування вже завантаженого масиву |
| REQ-F-027 | Сортування елементів всередині колекції | Клієнт | Локальне сортування завантаженого списку |
| REQ-F-028 | Валідація обкладинки (формат, розмір ≤ 5 МБ) | API + клієнт | Клієнт — негайний UX-feedback; API — обов'язкова серверна перевірка (клієнтську валідацію можна обійти) |
| REQ-F-029 | Зміна нікнейму | API | Оновлення профілю в БД — PATCH /users/me |

## 2. Модель ресурсів

| Ресурс | Базовий шлях | Що описує | Покриває REQ-F |
|---|---|---|---|
| Auth | `/auth` | Сесія аутентифікації: реєстрація, вхід, вихід | F-001, F-002, F-003 |
| User | `/users/me` | Профіль поточного користувача (нікнейм) | F-029 |
| Item | `/items` | Елемент каталогу (книга / серіал / фільм) з усіма атрибутами, типоспецифічними полями та обкладинкою | F-004, F-005, F-006, F-007, F-008, F-009, F-011, F-021, F-023, F-024, F-025, F-026, F-028 |
| Tag | `/tags` *(read-only)* | Агрегований список тегів користувача для автодоповнення | F-010, F-011 |
| Session | `/items/:id/sessions` | Окремий запис перегляду / читання: дата, рейтинг, нотатка | F-012, F-013, F-014 |
| Collection | `/collections` | Іменована добірка елементів каталогу | F-015, F-016, F-017, F-018, F-019, F-020, F-027 |
| Stats | `/stats` | Агреговані особисті показники: кількість завершених за типом і часовим діапазоном | F-022, F-022a |

## 3. Архітектурні рішення

**Теги — атрибут Item, не окремий ресурс.** Тег у SRS — це рядок без власного ідентифікатора; він не існує незалежно від елемента і не має власного CRUD-циклу (F-010: теги додаються і прибираються через редагування елемента). Єдина операція поза контекстом елемента — `GET /tags`, яка повертає унікальні теги користувача для автодоповнення; цей read-only endpoint є похідним агрегатом, а не повноцінним ресурсом.

**Sessions — вкладений ресурс `/items/:id/sessions`.** У SRS Sessions завжди розглядаються в контексті конкретного елемента (F-012: «записати Session для елемента», F-013: «список усіх Sessions елемента»); жоден use-case не вимагає переглядати Sessions по всіх елементах одночасно. Вкладений шлях явно виражає приналежність і унеможливлює доступ до сесії без авторизації через батьківський елемент.

**Many-to-many добірок — вкладений під-ресурс `/collections/:id/items` без окремого ресурсу.** Операції в SRS завжди формулюються від імені добірки: «додати елемент до добірки» (F-015), «вилучити елемент з добірки» (F-019), «відобразити вміст добірки» (F-020). Виділяти окремий ресурс `/memberships` немає сенсу — жоден use-case не посилається на «зв'язок» напряму, а вкладений шлях природно виражає склад добірки без зайвої сутності.

**Виноски:**

> ¹ Фільтрування за типом (F-005), статусом (F-006), тегом (F-011), пошук за назвою (F-023) та сортування (F-026) — **клієнтська логіка**; `GET /items` повертає повний каталог, query-параметри не передбачені.
>
> ² Поля типу: `author`, `pages` (book); `seasons` (series); `director`, `duration` (film) — F-024.
>
> ³ F-021 — клієнтська логіка форми (автопідстановка дати); сервер отримує `completedAt` через цей самий `PATCH` і лише зберігає значення.
>
> ⁴ **200, не 201**: обкладинка не є самостійним ресурсом — це атрибут `Item`, що замінюється. 201 означав би створення нового ресурсу.
>
> ⁵ Список добірок явно вимагається AC-016 («нова добірка з'являється у списку добірок») та є передумовою навігації для F-017/F-018/F-020.
>
> ⁶ **201, не 200**: запит створює новий зв'язок many-to-many в БД — аналогічно до `POST /items/:id/sessions` (рядок 14).
>
> ⁷ `period` — обов'язковий enum із трьох значень: `month`, `year`, `all`. Будь-яке інше значення → 400 `INVALID_PERIOD`.

## 5. Схеми об'єктів

```jsonc
// User
{
  "id": "uuid",
  "email": "string",
  "nickname": "string"
}

// Item
{
  "id": "uuid",
  "title": "string",
  "type": "book | series | film",
  "status": "planned | in_progress | completed | on_hold",
  "rating": "0–10 | null",
  "notes": "string | null",
  "tags": ["string"],
  "coverUrl": "string | null",      // null = відображати дефолт за типом на клієнті
  "completedAt": "YYYY-MM-DD | null",
  "createdAt": "ISO 8601",
  // book:
  "author": "string | null",
  "pages": "integer | null",
  // series:
  "seasons": "integer | null",
  // film:
  "director": "string | null",
  "duration": "integer | null"      // хвилини
}

// Session
{
  "id": "uuid",
  "itemId": "uuid",
  "date": "YYYY-MM-DD",
  "rating": "0–10 | null",
  "note": "string | null"
}

// Collection
{
  "id": "uuid",
  "name": "string"
}

// CollectionDetail  (GET /collections/:id)
{
  "id": "uuid",
  "name": "string",
  "items": [
    { "id": "uuid", "title": "string", "type": "...", "status": "...", "rating": "0–10 | null", "createdAt": "ISO 8601" }
  ]
}

// Stats  (GET /stats)
// period фільтрує за Item.completedAt (не за датою Session)
{
  "period": "month | year | all",
  "books": "integer",
  "series": "integer",
  "films": "integer",
  "total": "integer"
}
```

## 6. Формат помилки

Усі коди 4xx повертають однаковий JSON:

```jsonc
{
  "code":    "PASSWORD_TOO_SHORT",  // machine-readable ідентифікатор
  "message": "Пароль має містити щонайменше 8 символів",
  "field":   "password"            // наявність залежить від коду (таблиця нижче)
}
```

| HTTP | Правило для поля `field` |
|---|---|
| **400** | Присутнє завжди — вказує поле, що порушує правило (REQ-NF-006) |
| **409** | Присутнє, якщо конфлікт стосується конкретного поля (`EMAIL_TAKEN` → `"field": "email"`); відсутнє для `ITEM_ALREADY_IN_COLLECTION` |
| **401, 404** | Відсутнє — помилка не пов'язана з окремим полем |

> **403 не використовується.** У системі одна роль — User; ресурси іншого користувача повертають **404** (не розкриваємо факт існування чужих даних).

| Сценарій | HTTP | `code` |
|---|---|---|
| Невалідний email | 400 | `INVALID_EMAIL` |
| Пароль < 8 символів | 400 | `PASSWORD_TOO_SHORT` |
| Нікнейм поза 2–50 символів | 400 | `INVALID_NICKNAME_LENGTH` |
| Відсутнє обов'язкове поле | 400 | `MISSING_REQUIRED_FIELD` |
| Невалідний формат файлу | 400 | `INVALID_FILE_FORMAT` |
| Файл > 5 МБ | 400 | `FILE_TOO_LARGE` |
| Невідоме значення `period` | 400 | `INVALID_PERIOD` |
| Решта помилок валідації | 400 | `VALIDATION_ERROR` |
| Неправильний email або пароль | 401 | `INVALID_CREDENTIALS` |
| Сесія відсутня / протермінована | 401 | `UNAUTHORIZED` |
| Ресурс не знайдено | 404 | `NOT_FOUND` |
| Email вже зареєстрований | 409 | `EMAIL_TAKEN` |
| Елемент вже є в добірці | 409 | `ITEM_ALREADY_IN_COLLECTION` |
