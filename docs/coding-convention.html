01 Базовий стандарт

Основою конвенції є Google TypeScript Style Guide — офіційно визнаний стандарт для TypeScript-проєктів. Усі правила нижче або відповідають йому, або є задокументованими відхиленнями, зумовленими особливостями стеку.

Первинне джерело: google.github.io/styleguide/tsguide.html
Де Google TS Guide мовчить — застосовується TypeScript Handbook.

TypeScript скомпільований у strict mode (tsconfig.json: "strict": true), що автоматично включає: strictNullChecks, noImplicitAny, strictFunctionTypes та інші перевірки.

02 Іменування

Сутність Стиль Приклад
Змінна, параметр, поле об'єкта camelCase userId, coverUrl, newItem
Функція, метод camelCase handleSave, getItemById, toApi
Інтерфейс, тип, enum PascalCase ApiItem, DbItem, AppError
React-компонент (функція) PascalCase ItemDetail, AddSheet, Cover
Константа рівня модуля SCREAMING_SNAKE_CASE ALLOWED_MIME, MAX_COVER_SIZE
Файл camelCase itemService.ts, sessionRepo.ts
Директорія camelCase routes/, services/, repositories/
DB-поле (SQL/SQLite) snake_case user_id, cover_url, created_at
✓
Префікс is / has / can / should для булевих змінних і параметрів.
const isLoading = true;
const hasRating = item.rating !== null;
const canDelete = sessions.length === 0;
✗
Однолітерні імена (крім лічильників циклу i, j та параметрів нижчого рівня _req).
// ✗ уникати
const f = e.target.files?.[0];
// ✓ замінити на
const file = e.target.files?.[0];

03 Типізація

✓
Явні interface для форм API-відповідей і DB-рядків. type — для union-типів та псевдонімів.
// API shape — interface
export interface ApiItem {
  id: string;
  title: string;
  type: 'book' | 'series' | 'film';
  rating: number | null;
  tags: string[];
  // ...
}

// Union alias — type
type ItemStatus = 'planned' | 'in_progress' | 'completed' | 'on_hold';
✓
Runtime-валідація вхідних даних через Zod-схеми. Статичні типи виводяться з них через z.infer.
export const createItemSchema = z.object({
  title: z.string().min(1),
  type: z.enum(['book', 'series', 'film']),
  rating: z.number().int().min(0).max(10).nullable().optional(),
  tags: z.array(z.string()).optional(),
});

export type CreateItemData = z.infer;
✗
Заборонено any (strict mode). Для невідомих форм використовується unknown з подальшим звуженням типу.
// ✗ уникати
} catch (err: any) { console.log(err.status); }

// ✓ використовувати
} catch (err: unknown) {
  const apiErr = err as { status?: number };
  if (apiErr.status === 400) { /* ... */ }
}
✓
Явне позначення null як можливого значення (string | null). Не змішувати з undefined без потреби.
// DB-поля, що можуть бути відсутні — null
cover_url: string | null;
completed_at: string | null;

// Необов'язкові поля форми — undefined через optional()
notes?: string | null;  // може бути відсутнє або явно null

05 Файли та директорії

Backend дотримується чіткої шарової архітектури:

src/
├── server.ts         # точка входу — підключає db і app
├── app.ts            # налаштування Express + middleware
├── config/           # змінні середовища (ENV)
├── db/               # ініціалізація SQLite + міграції
├── middleware/       # auth, error-handler
├── routes/           # HTTP-маршрути (тонкий шар)
├── services/         # бізнес-логіка; не знає про HTTP
├── repositories/     # прямі SQL-запити; не знає про бізнес-логіку
├── validators/       # Zod-схеми вхідних даних
├── types/            # глобальні типи (розширення express-session)
└── utils/            # дрібні утиліти (errors.ts, тощо)
✓
Один файл — одна відповідальність. Не поєднувати route-handler і бізнес-логіку в одному файлі.
// routes/items.ts — лише HTTP: парсинг, відповідь, статус-коди
router.get('/', requireAuth, (req, res) => {
  const items = itemService.listItems(db, req.session.userId!);
  res.json(items);
});

// services/itemService.ts — лише логіка, не знає про res/req
export function listItems(db: Database, userId: string): ApiItem[] {
  return itemRepo.getUserItems(db, userId).map(toApi);
}

06 Імпорти

✓
Порядок блоків імпорту: (1) вбудовані Node-модулі, (2) зовнішні пакети, (3) внутрішні (../). Між групами — порожній рядок.
import path from 'path';
import fs from 'fs';

import { Router } from 'express';
import multer from 'multer';
import Database from 'better-sqlite3';

import { requireAuth } from '../middleware/auth';
import { createItemSchema } from '../validators/itemValidators';
import * as itemService from '../services/itemService';
✓
Namespace-імпорт (import * as) для сервісів і репозиторіїв. Іменований імпорт — для конкретних функцій і типів.
import * as itemService from '../services/itemService';   // namespace
import * as itemRepo   from '../repositories/itemRepo';    // namespace

import { notFound }    from '../utils/errors';             // named
import { DbItem }      from '../repositories/itemRepo';    // named type

07 Функції

✓
Іменовані function-декларації на рівні модуля в backend; стрілкові функції — для коротких утиліт і колбеків.
// ✓ іменована декларація — рівень модуля
export function createItem(db: Database, id: string, data: CreateItemData): ApiItem {
  // ...
}

// ✓ стрілкова — утиліта в одному рядку
const mimeToExt = (mime: string): string =>
  ({ 'image/jpeg': '.jpg', 'image/png': '.png' })[mime] ?? '';
✓
React-компоненти — завжди function-декларації (не стрілкові), щоб ім'я було видиме в стек-трейсах.
// ✓ правильно
function ItemDetail({ itemId, onBack }: ItemDetailProps) {
  // ...
}

// ✗ уникати в компонентах
const ItemDetail = ({ itemId, onBack }: ItemDetailProps) => { ... };

08 Обробка помилок

✓
Всі доменні помилки формуються через централізовану фабрику makeError / notFound з utils/errors.ts.
// utils/errors.ts — фабрика
export function makeError(code: string, message: string, status: number): AppError {
  const err = new Error(message) as AppError;
  err.code = code;
  err.status = status;
  return err;
}
export const notFound = () => makeError('NOT_FOUND', 'Resource not found', 404);

// service — throw стандартної помилки
function assertOwner(item: DbItem | undefined, userId: string): DbItem {
  if (!item || item.user_id !== userId) throw notFound();
  return item;
}
✓
У frontend catch-блоках, де помилка не впливає на UX, тіло залишається порожнім з явним коментарем або взагалі без тіла (non-fatal).
try {
  const { coverUrl } = await api.items.uploadCover(newItem.id, coverFile);
  newItem.coverUrl = coverUrl;
} catch { /* non-fatal — cover upload failure doesn't block item creation */ }

// ✓ пояснює неочевидне перетворення дати SQLite → ISO 8601
createdAt: new Date(item.created_at.replace(' ', 'T') + 'Z').toISOString(),

// ✗ зайвий — назва і так зрозуміла
// get item by id
export function getItemById(db: Database, id: string): DbItem | undefined { ... }

Секційні розділювачі у великих файлах — однолінійні ASCII-коментарі у форматі // ─── Назва ──────.

10 Backend — Node.js / Express

✓
Route-handler завжди закінчується або res.json() / res.status().json(), або викликом next(err). Не залишати відповідь "висіти".
router.post('/', requireAuth, (req, res, next) => {
  try {
    const data = createItemSchema.parse(req.body);
    const item = itemService.createItem(db, uuidv4(), req.session.userId!, data);
    res.status(201).json(item);
  } catch (err) {
    next(err);  // передаємо в centralized error-handler
  }
});
✓
Змінні середовища виключно через config/env.ts (об'єкт ENV). Пряме звернення до process.env у сервісах/роутах заборонене.
// config/env.ts — одне місце
export const ENV = {
  PORT: process.env.PORT ?? '3000',
  SESSION_SECRET: process.env.SESSION_SECRET ?? 'dev-secret',
};

// server.ts — через ENV
app.listen(Number(ENV.PORT), () => { /* ... */ });

11 Frontend — React / Vite

✓
Усі API-виклики через єдиний об'єкт api з lib/api.ts. Прямий fetch у компонентах заборонений.
// ✓ через централізований клієнт
const item = await api.items.get(itemId);
const session = await api.sessions.create(itemId, { date, rating, note });

// ✗ прямий fetch в компоненті — заборонено
const res = await fetch('/api/v1/items/' + itemId);
✓
State локальний у компоненті або піднятий на рівень root App. Зовнішній state-менеджер не використовується (достатньо prop drilling для поточного масштабу).
// App.tsx — спільний стан
const [items, setItems] = useState<ApiItem[]>([]);
const [collections, setCollections] = useState<ApiCollection[]>([]);

// Передача донизу
<ItemDetail
  itemId={openItemId}
  collections={collections}
  onUpdated={handleItemUpdated}
/>
✓
Вся стилізація — CSS-класи в index.css. Inline-стилі використовуються лише для динамічних значень, що не можна передбачити статично.
// ✓ статичний вигляд — клас
<span className="status-pill status-completed">Completed</span>

// ✓ динамічне значення — inline
<i style={{ width: `${progressPercent}%` }} />

// ✗ статичні кольори/відступи inline
<div style={{ padding: "14px 16px", background: "#fbfaf6" }}>
