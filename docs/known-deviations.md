# Known Deviations from Specification

Відхилення, що задокументовані та свідомо не виправляються у v1 MVP.  
Джерело специфікації: `spec/srs.md`, `docs/api-design.md`, `spec/openapi.yaml`.

---

## DEV-01 — Коди помилок валідації: VALIDATION_ERROR замість специфічних кодів

**Що:** `docs/api-design.md §6` передбачає окремі machine-readable коди для кожного
типу validation error:

| Сценарій | Код за api-design.md §6 | Реальний код сервера |
|----------|------------------------|---------------------|
| Невалідний email | `INVALID_EMAIL` | `VALIDATION_ERROR` |
| Пароль < 8 символів | `PASSWORD_TOO_SHORT` | `VALIDATION_ERROR` |
| Нікнейм поза 2–50 символів | `INVALID_NICKNAME_LENGTH` | `VALIDATION_ERROR` |
| Невідоме значення `period` | `INVALID_PERIOD` | `VALIDATION_ERROR` |

Виняток: `INVALID_BASIS`, `EMAIL_TAKEN`, `ITEM_ALREADY_IN_COLLECTION`,
`INVALID_CREDENTIALS`, `NOT_FOUND`, `UNAUTHORIZED` — відповідають специфікації.

Поле `field` у відповіді завжди присутнє і вказує на конкретний параметр,
що порушує правило (відповідає REQ-NF-006 та `openapi.yaml` schema `Error`).

**Чому не виправляємо:** Zod (`src/validators/`) повертає одну уніфіковану помилку для
всіх validation errors. Введення окремих кодів потребувало б або ручної перевірки кожного
поля після Zod, або написання власного Zod error mapper — суттєвий обсяг роботи без
функціонального виграшу для MVP.

`openapi.yaml` у схемі `Error` допускає будь-який рядок у полі `code`, тому
специфікація контракту формально не порушена. Порушення лише у `api-design.md §6` —
внутрішньому дизайн-документі.

**Вплив:** Клієнт, що покладається на `INVALID_EMAIL` або `PASSWORD_TOO_SHORT` для
локалізованих повідомлень про помилки, не зможе їх розрізнити без аналізу поля `field`.
Поле `field` доступне і достатнє для такої логіки.

## DEV-02 — Prism v5 не валідує cookie-аутентифікацію

**Що:** `logs/api-contract-run.md` підтверджує, що Prism proxy (v5) не перевіряє
наявність cookie у захищених запитах. Запити до `GET /items` без `Cookie: session=...`
Prism пропускає як валідні (не повертає 401).

**Чому не виправляємо:** Це обмеження Prism v5 — він не реалізує перевірку
`apiKey in: cookie` security scheme. Prism перевіряє лише тіла запитів/відповідей та
query/path параметри. Коректна поведінка аутентифікації (401 без сесії) перевірена
тестами Vitest (`tests/integration/auth.test.ts`, AC-035/NF-002).

**Вплив:** При запуску Prism як mock-сервера він дозволяє неаутентифіковані запити.
Прямий прогін проти реального сервера (не Prism) дає правильний 401. Contract-тести
через Prism не охоплюють auth-негативні сценарії.

## DEV-03 — Поточна дата в статистиці — UTC годинник сервера

**Що:** `GET /stats?period=month` та `period=year` фільтрують дані за поточною датою
від `getClock()()` — `new Date()` на сервері, що завжди повертає UTC.

Якщо локальний час користувача відрізняється від UTC (напр., UTC+2 вночі після опівночі),
статистика за «поточний місяць» може не включити записи, що за місцевим часом
є в поточному місяці, але за UTC вже відносяться до наступного.

**Чому не виправляємо:** REQ-F-022 не специфікує часовий пояс. Усі дати в системі
зберігаються без timezone (SQLite `TEXT`). Введення timezone-aware логіки потребує
передачі tz від клієнта, зберігання offset у сесії або в профілі — поза scope MVP.

Механізм тестово замінюваного годинника (`utils/clock.ts`, `setClock()`) дозволяє
детерміновано тестувати статистику в будь-якій даті без реальної залежності від UTC.

**Вплив:** Незначний для типового користувача в UTC±3. Може помітитись у крайових
випадках (опівнічний перегляд, timezone UTC-8 і пізніше). Для production-версії
рекомендується зберігати preferred_timezone у профілі користувача.
